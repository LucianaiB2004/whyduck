## 按严重程度排序的初始问题

1. **P1：管家入口无法自动协作。** `src/client/Chat.tsx:64` 在管家角色页发送 `mode=direct,target=butler`，`src/server/ai/index.ts:77` 显式 target 直接单鸭执行并结束。管家即使推荐专业鸭也不会执行接力，更不会转入群聊。复现：首页进入管家鸭，描述退款问题并发送，观察请求参数与实际角色运行列表。
2. **P1：路由可能漏掉完成目标所必需的角色。** `src/server/ai/index.ts:78` 完全信任管家 `suggestedMembers`，没有专业职责覆盖检查。已有实网报告仅证明管家、后手、管家，不能证明证据侦探或退款军师实际执行。需要真实退款场景和缺漏路由回归测试。
3. **P1：工具执行并非必需。** `src/server/ai/index.ts:46` 的模型请求允许直接返回 JSON，`src/server/ai/index.ts:71` 接受没有工具的 completed 运行。工具确实运行真实案件逻辑，但可能被模型完全绕过。需要记录本次各专业角色实际工具执行，不能将工具声明当作调用证据。
4. **P1：材料详情表单可跨材料污染。** 初始 `EvidenceDetail` 只通过 useState 初始化 extraction，没有按 evidence.id 重建；A 的编辑内容可能写入 B。审查期间主执行者已添加材料 ID key；最终浏览器回归结果以主验收记录为准。
5. **P1：案件表单与核对状态可跨案件残留。** `CaseTools` 的草稿文字、草稿 ID、事实关联材料和 report reviewed 等本地状态未按案件重置。切换案件可能复制旧案件草稿、沿用旧案件导出核对状态。建议按案件 ID 重建表单组件。
6. **P2：SSE 完成结果在整轮结束前不展示。** `src/client/Chat.tsx:68` 只保存当前事件，直到 finally refresh 才显示已落库角色回复。真实长流程中看不到已完成专业结果，取消后才突然出现；应在结果事件更新界面，保持顺序与保存结果一致。

## 已观察到的正确边界

- 正式 agent.message 来自服务端模型 HTTP 响应，未发现正常实时聊天直接返回硬编码伪模型回复。固定售后步骤和草稿模板存在于显式规则工具，属于工具提案，不能据此宣称模型推断。
- 每个角色使用独立系统提示、授权工具集合、调用 UUID、token 用量和持久化运行记录；接力上下文包含已完成结果与共享案件数据。是否在具体场景真正执行必须依赖实网记录。
- 未配置模型与 demo 案件均拒绝实时分析；demo 消息、报告有明确标识。
- 未知材料与不存在的逐字引文会被拒绝。图片 OCR 结果默认 proposed；只有人工确认的提取引文可被作为核对过的图像出处。
- 事实、草稿、任务、证据与消息存储在私有案件 SQLite 记录；材料下载检查所属账户。原图与哈希保存，模型使用派生图。
- 待办建议需人工确认；没有外部发送、投诉、退款或提醒成功的伪状态。

### 汇总协议与文字引用复审

### 出处纠正机制复审（最新行为）

实网退款鸭曾引用未人工确认的图片文字，被出处校验拒绝。最新修改允许独立最多一次出处纠正，与之前“不纠正出处”的阶段行为不同：只向模型提供原始文字及已人工确认图片提取中的可引用原文，重新生成后仍完整执行相同 strict 结构与逐字引用验证。不自动修改或补造引用，不把未确认 OCR 提升为已确认事实。

首轮不合格输出不落成功消息、不写事实/草稿/任务；持续错误会 throw 并保存 failed 运行、发送 error，不吞掉异常。错误角色身份和越权工具没有进入出处纠正白名单。纠正次数记录在服务端 AgentRun.validationCorrections；因此报告应区分“首轮成功”与“经过校验纠正后成功”，不能把被拒绝的首轮输出描述为已通过。原始实网失败仍需留存为失败记录。

独立运行 `npm test -- tests/ai.test.ts tests/workflow-http.test.ts`：22 项通过（LOCAL MOCK），验证首次坏引文没有持久化、第二次合法逐字引文才持久化、纠正计数，以及持续坏引用失败后保留原始任务的重试关联。无新增阻断性安全问题。建议把纠正次数显示在导出运行记录，避免只有底层 JSON 可见；实网重跑结果仍由主执行者记录。
